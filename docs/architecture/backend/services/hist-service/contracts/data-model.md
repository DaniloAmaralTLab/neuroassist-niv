# HIST — Data Model

> Service: `hist-service` · Module **HIST** · PostgreSQL · schema-per-tenant (`tenant` term,
> global schema `neuroassist_global`). Flyway authored by HIST, applied centrally by MIG
> (`neuroassist-niv-migrations`) across `neuroassist_global` and every `t_<tenantId>`.
> SQL blocks below are the canonical DDL consumed by `be-migration-generator.py` /
> `be-entity-generator.py`. EARS: `../../../standards/ears-notation.md`.

## 1. Conventions

- **PK strategy** — `text` ULID/UUID string ids generated by the producer or HIST
  (`id text PRIMARY KEY`); no DB sequences on the audit path.
- **Timestamps** — `timestamptz`. `occurred_at` = producer time; `received_at` = HIST ingest time
  (`DEFAULT now()`). No `updated_at` (append-only, INV-HIST-1).
- **Soft-delete** — **none**. There is no delete/update on audit tables (ADR-002 Option A).
- **Encoding** — UTF-8; `payload` is `jsonb`.
- **Immutability (ADR-002 Option A)** — enforced by DB grants (INSERT/SELECT only on audit tables;
  no UPDATE/DELETE to the HIST app role). See §5.
- **Tamper-evidence (ADR-002 Option B, additive)** — `record_hash` / `prev_hash` columns are
  **reserved now** (nullable, unused in MVP) so a hash chain is an additive change with no migration
  break.
- **Crypto-shred (ADR-006)** — personal payload fields are stored encrypted under a per-subject key;
  erasure = delete the key (`audit_subject_key`), never the audit row.

## 2. Entities

### 2.1 `audit_record` [tenant]

The append-only trail for every **tenant-scoped** fact (ACS, PAT, EDGE, EVNT). One row per producer
fact, upserted on the idempotency key (ADR-003). `source` + `subject_type` disambiguate the
`DetectionLapseResolved` collision (doc 06 R4). Personal fields live inside `payload` encrypted under
the subject key; `payload_encrypted` flags whether crypto-shred applies.

```sql
-- schema: tenant
CREATE TABLE audit_record (
    id               text        NOT NULL,
    source           text        NOT NULL,
    action           text        NOT NULL,
    actor_type       text        NOT NULL,
    actor_id         text        NULL,
    tenant_id        text        NOT NULL,
    subject_type     text        NOT NULL,
    subject_id       text        NOT NULL,
    occurred_at      timestamptz NOT NULL,
    received_at      timestamptz NOT NULL DEFAULT now(),
    correlation_id   text        NOT NULL,
    payload_version  integer     NOT NULL DEFAULT 1,
    payload          jsonb       NOT NULL DEFAULT '{}'::jsonb,
    payload_encrypted boolean    NOT NULL DEFAULT false,
    idempotency_key  text        NOT NULL,
    flagged          boolean     NOT NULL DEFAULT false,
    record_hash      text        NULL,
    prev_hash        text        NULL,
    PRIMARY KEY (id),
    UNIQUE (idempotency_key),
    CONSTRAINT ck_audit_record_actor_type
        CHECK (actor_type IN ('caregiver','edge-device','system','service-client'))
);

CREATE INDEX ix_audit_record_subject_time ON audit_record (tenant_id, subject_id, occurred_at DESC);
CREATE INDEX ix_audit_record_correlation  ON audit_record (correlation_id);
CREATE INDEX ix_audit_record_action_src   ON audit_record (action, source, subject_type);
CREATE INDEX ix_audit_record_flagged      ON audit_record (flagged) WHERE flagged = true;

COMMENT ON TABLE audit_record IS 'Append-only tenant-scoped audit trail (INV-HIST-1). No UPDATE/DELETE.';
COMMENT ON COLUMN audit_record.idempotency_key IS 'ADR-003 hybrid key: explicit when supplied, else composite source|subject_type|subject_id|action|occurred_at.';
COMMENT ON COLUMN audit_record.record_hash IS 'ADR-002 Option B reserved (nullable); unused in MVP.';
```

**Invariants:** INV-HIST-1 (append-only — enforced by grants §5, not a trigger), INV-HIST-2
(`source`/`action`/`actor_type`/`occurred_at`/`correlation_id` NOT NULL), INV-HIST-3 (UNIQUE
`idempotency_key`), INV-HIST-5 (tenant-scoped → `tenant_id` NOT NULL here).

### 2.2 `audit_record_global` [global]

Home for **global-schema** facts that carry no tenant — the GEST engine registry facts
(`EngineVersionRegistered/Deprecated`, `EngineCapabilityDeclared/Retired`). Same shape as
`audit_record` with `tenant_id` nullable (ADR-004 Option A). GEST facts carry no personal data, so
no subject key is required.

```sql
-- schema: global
CREATE TABLE audit_record_global (
    id               text        NOT NULL,
    source           text        NOT NULL,
    action           text        NOT NULL,
    actor_type       text        NOT NULL,
    actor_id         text        NULL,
    tenant_id        text        NULL,
    subject_type     text        NOT NULL,
    subject_id       text        NOT NULL,
    occurred_at      timestamptz NOT NULL,
    received_at      timestamptz NOT NULL DEFAULT now(),
    correlation_id   text        NOT NULL,
    payload_version  integer     NOT NULL DEFAULT 1,
    payload          jsonb       NOT NULL DEFAULT '{}'::jsonb,
    idempotency_key  text        NOT NULL,
    flagged          boolean     NOT NULL DEFAULT false,
    record_hash      text        NULL,
    prev_hash        text        NULL,
    PRIMARY KEY (id),
    UNIQUE (idempotency_key),
    CONSTRAINT ck_audit_record_global_actor_type
        CHECK (actor_type IN ('caregiver','edge-device','system','service-client'))
);

CREATE INDEX ix_audit_record_global_subject_time ON audit_record_global (subject_id, occurred_at DESC);
CREATE INDEX ix_audit_record_global_correlation  ON audit_record_global (correlation_id);
CREATE INDEX ix_audit_record_global_action_src   ON audit_record_global (action, source, subject_type);

COMMENT ON TABLE audit_record_global IS 'Append-only global-schema audit trail for tenant-less GEST facts (ADR-004 Option A).';
```

**Invariants:** INV-HIST-5 (global facts → `tenant_id` NULL), INV-HIST-1, INV-HIST-3.

### 2.3 `audit_subject_key` [tenant]

Per-subject data-encryption key for crypto-shred (ADR-006). Personal payload fields are encrypted
under `key_material`; erasure deletes the row so the ciphertext in `audit_record.payload` becomes
permanently unreadable, while the immutable audit row is retained. Lives per-tenant because its
subjects (patients, caregivers) are tenant-scoped. This is the **only** audit-adjacent table the HIST
role may `DELETE` from (§5).

```sql
-- schema: tenant
CREATE TABLE audit_subject_key (
    subject_type   text        NOT NULL,
    subject_id     text        NOT NULL,
    key_material   bytea       NOT NULL,
    status         text        NOT NULL DEFAULT 'active',
    created_at     timestamptz NOT NULL DEFAULT now(),
    shredded_at    timestamptz NULL,
    legal_basis_ref text       NULL,
    PRIMARY KEY (subject_type, subject_id),
    CONSTRAINT ck_audit_subject_key_status CHECK (status IN ('active','shredded'))
);

COMMENT ON TABLE audit_subject_key IS 'ADR-006 crypto-shred: per-subject DEK. Erasure deletes the key; audit rows are retained.';
```

**Invariants:** erasure sets `status='shredded'` + `shredded_at` then deletes `key_material`
(or deletes the row); audit rows are never touched (ADR-002 / ADR-006).

### 2.4 `audit_retention_policy` [global]

Retention configuration per **fact class** with legal-hold (ADR-006 Option C frame). Retention
**periods and lawful basis are an OPEN item with counsel** — the table is modelled now (config-driven)
with nullable periods so the policy can be set without a migration. No automated retention sweep ships
in MVP (periods TBD); the table is the seam for it.

```sql
-- schema: global
CREATE TABLE audit_retention_policy (
    fact_class       text        NOT NULL,
    retention_days   integer     NULL,
    legal_hold       boolean     NOT NULL DEFAULT false,
    lawful_basis_ref text        NULL,
    updated_at       timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (fact_class),
    CONSTRAINT ck_audit_retention_days CHECK (retention_days IS NULL OR retention_days > 0)
);

COMMENT ON TABLE audit_retention_policy IS 'ADR-006: retention per fact class + legal hold. Periods TBD with counsel (nullable).';
```

**Fact classes** (seeded values, periods NULL until counsel sets them): `access-lifecycle`,
`device-lifecycle`, `catalog-config`, `safety-runtime`, `engine-registry`, `authentication`.

### 2.5 `audit_source` [global] (optional MVP)

Producer registry for attribution/validation. Optional at MVP; present so `source` can be validated
and the allowed-action set documented. Not on the hot ingest path.

```sql
-- schema: global
CREATE TABLE audit_source (
    source          text        NOT NULL,
    display_name    text        NOT NULL,
    allowed_actions jsonb       NOT NULL DEFAULT '[]'::jsonb,
    created_at      timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (source)
);

COMMENT ON TABLE audit_source IS 'Producer registry (service id -> allowed actions). Optional at MVP; attribution/validation only.';
```

## 3. Relations (ASCII)

```
audit_record (t_<tenantId>)         audit_record_global (neuroassist_global)
  | tenant_id  subject_id             | subject_id (GEST engine_version / engine_capability)
  | source + subject_type             |
  v                                   v
audit_subject_key (t_<tenantId>)    audit_source (global)   audit_retention_policy (global)
  (subject_type, subject_id) --crypto-shred--> payload unreadable, row retained
```
No FKs cross the tenant/global boundary; `audit_subject_key` is matched to `audit_record` in the
application layer by (`subject_type`, `subject_id`), not a DB FK (append-only table takes no FK that
could block an insert).

## 5. DB grants (ADR-002 Option A — append-only)

```sql
-- schema: tenant  (and mirrored for global tables)
GRANT INSERT, SELECT ON audit_record TO hist_app;
GRANT INSERT, SELECT ON audit_subject_key TO hist_app;
GRANT DELETE ON audit_subject_key TO hist_app;   -- crypto-shred key deletion ONLY (ADR-006)
REVOKE UPDATE, DELETE ON audit_record FROM hist_app;
```

- THE SYSTEM SHALL grant the HIST app role only `INSERT`/`SELECT` on `audit_record` and
  `audit_record_global`; `UPDATE`/`DELETE` on audit rows are denied (ADR-002, INV-HIST-1).
- WHERE crypto-shred is performed, THE SYSTEM SHALL `DELETE` only from `audit_subject_key` — never from
  an audit table (ADR-006).

## 6. Personal payload fields per fact (crypto-shred scope — ADR-006)

Stable ids (`subject_id`, `actor_id`, `correlation_id`) are **pseudonymous** and retained. The
following **personal** payload fields are encrypted under the subject key and become unreadable on
erasure. Engine-registry (GEST) facts carry **no** personal data.

| Producer / fact group | Personal payload fields (crypto-shred) |
|---|---|
| ACS `CaregiverRegistered` | caregiver `name`, `email`, `phone` |
| ACS `PatientLinked` / `PatientUnlinked` / `PatientSession*` | patient `displayName` (if present); device label |
| PAT `PatientRegistered` | patient `name`, `displayName` |
| PAT `CommandCalibrated` / `CommandRetired` | free-form `label` / `needText` (family-defined, sensitive) |
| EDGE device-lifecycle | device `label`/alias (if present) |
| EVNT `EventGenerated` / `AlarmConfirmed` / `FeedbackRecorded` | `commandLabel`, free-text `note` |
| EVNT `EscalationAttempted` | contact endpoint (phone/push token) |
| GEST engine registry | none |

## 7. Caregiver timeline projection (read model — G-HIST-1..5)

The caregiver read `GET /hist/patients/{patientId}/history` (api-contract §2) projects a structured
`HistoryEntry` from `audit_record` **without new physical columns** — every structured field maps to an
existing column or a `payload` JSON path. No migration beyond the additive index `V0065` (§4) is needed.

| Entry field | Projected from | Notes |
|---|---|---|
| `subjectId` | `subject_id` | event entries → `eventId` |
| `relatedEventId` | `subject_id` WHERE `subject_type = 'event'` | join key (G-HIST-2); no column added |
| `commandId` | `payload ->> 'commandId'` | present on EVNT event-kind facts (`event-contracts` §1.2) |
| `commandLabel` | `payload ->> 'commandLabel'` | **upstream EVNT amendment** — EVNT must add `commandLabel` to the `EventGenerated` audit payload (it is a crypto-shred personal field, §6); HIST omits the field when absent (never fabricates) |
| `urgency` | `payload ->> 'urgency'` | present on EVNT `EventGenerated` |
| `confirmation.confirmedAt` / `.confirmedBy` | the sibling `AlarmConfirmed` row's `occurred_at` / `payload ->> 'confirmedBy'` | server-side fold onto the `EventGenerated` entry, matched by `subject_id` |
| `channel` | `payload ->> 'channel'` | present on EVNT `EscalationAttempted` (`web_push`\|`sms`\|`voice`) |
| `maskedTarget` | `payload ->> 'maskedTarget'` | **upstream EVNT amendment** — EVNT must add the already-masked target to the `EscalationAttempted` audit payload (raw `channel_target` stays out of the audit for privacy, §6); HIST passes it through, never unmasks |
| `outcome` | derived per `kind` | feedback/event ← `payload ->> 'feedback'` (`real`\|`false_positive`\|`not_evaluated`); escalation ← `payload ->> 'status'` → `sent`\|`failed`; detection-lapse ← `action` → `started`\|`resolved`\|`acknowledged` |

**Period summary (G-HIST-4).** The first-page `summary` (api-contract §2) is a single aggregate over the
whole window — `SELECT action, count(*) ... FROM audit_record WHERE tenant_id = :tenant AND
payload ->> 'patientId' = :patientId AND occurred_at IN window GROUP BY action`, plus the confirmed /
feedback-verdict folds over the event-kind rows. Served by `ix_audit_record_patient_time` (V0065);
computed once per first page, not per keyset page.

- WHEN the caregiver timeline projects an entry, THE SYSTEM SHALL read `commandLabel`/`maskedTarget` from
  the stored `payload` and SHALL NOT synthesise either when the producer payload omits it.
- WHILE computing the period `summary`, THE SYSTEM SHALL aggregate over the whole requested window and
  SHALL NOT limit the aggregate to the returned page.
