# 05 — Persistence Model

> Service: `neuroassist-niv-migrations` · Module **MIG (Centralized Flyway)** · **Owns the migration surface of every schema; owns no business data.**

## Schema Strategy

MIG does not own a *business* schema, but it is the module **responsible for all schemas**.
The project is schema-per-tenant (`../../adr/ADR-003-multi-tenancy.md`,
`arch/decisions/multi-tenancy.arch.json`):

- **`neuroassist_global`** — shared catalogues. MIG **creates** it (baseline block) and keeps
  it on version. MIG's own only table, `migration_range_registry`, lives here.
- **`t_<tenantId>`** — one per care unit. MIG **creates** each (at provisioning) and applies
  the tenant-template migrations to all of them to the same version.

Routing is by the DDL annotation `-- schema: global | tenant` (`persistence.arch.json`): a
block's first line decides whether it is applied to `neuroassist_global` or to every
`t_<tenantId>`. The required extensions (`uuid-ossp`, `pgcrypto`, `pg_trgm`, `unaccent`) are
installed **once in `neuroassist_global`** and every tenant migration runs with
`search_path = t_<tenantId>, neuroassist_global`, so extension operator classes resolve
inside the tenant schema (Learning pitfall: extension objects not in search_path).

## Initial Entities

MIG owns exactly **one** persistent table (plus Flyway's own ledger):

- **`migration_range_registry`** (`neuroassist_global`) — authoritative reserved-block map.
  Columns (draft): `block_from VARCHAR(10)`, `block_to VARCHAR(10)`, `owner_module VARCHAR(10)`,
  `schema_target VARCHAR(10)` (`global`|`tenant`|`both`), `description TEXT`,
  `declared_at TIMESTAMPTZ NOT NULL DEFAULT now()`. Seeded in the baseline block with every
  known block. `migration_`-prefixed on purpose (avoids generic-name collision in the shared
  schema — Learning pitfall). Closes PAT **G1**.
- **`flyway_schema_history`** (per schema) — created/owned by Flyway; MIG reads it for the
  next-version computation and the per-schema report. Not a MIG-authored entity.

## Migration Strategy

- **Java stack → Flyway, centralized in MIG.** MIG is the **only** Flyway runner; every
  business `application.yml` keeps `spring.flyway.enabled: false` ("Migrations gerenciadas
  pelo neuroassist-niv-migrations" — verified on disk). MIG drives Flyway **programmatically
  per schema** (the Spring-Boot single-datasource runner cannot iterate tenants).
- **Local `V1__create_initial_schema.sql` reconciliation (ADR-003).** Each scaffolded service
  ships a flat `V1__create_initial_schema.sql` under `src/main/resources/db/migration/`,
  generated by `be-migration-generator.py` from its `contracts/data-model.md` (with
  `-- schema:` annotations). These are **generator scaffold**, not the runtime surface: the
  flat `V1` collides across services and sits where Flyway is disabled. The **runtime**
  surface is the reserved-block, schema-annotated set MIG applies. ADR-003 pins that these
  local files are regenerated into the module's reserved block (e.g. ACS → `V0010–V0012`) and
  collected into MIG's central locations; the local `V1` is deprecated, not run.
- **Forward-only & immutable (ADR-005).** No undo/rollback migrations. An applied `V*.sql` is
  never edited (checksum covers the whole file) — a correction is a new, strictly higher
  version. `outOfOrder = false`; the next version is `max(global ∪ tenant histories) + 1`.
  Repeatable (`R__`) migrations only for idempotent reseeds.
- **Checksum validation on.** A drifted/edited applied file fails the run fast and names the
  schema, rather than silently diverging across tenants.

## Data Lifecycle

- **MIG holds no PHI, no business data, no patient/caregiver data** — only the registry table
  and Flyway history. No LGPD retention/erasure/export obligation attaches to MIG's own store.
- **`migration_range_registry`** is append-mostly reference data, retained indefinitely
  (small). A block reassignment is a new forward migration, consistent with the immutability
  rule — never an in-place edit of an applied file.
- **`flyway_schema_history`** is retained for the life of each schema as the applied-state
  ledger; it is the audit trail of what ran where and is never pruned in the MVP.
- **Per-tenant dump/restore / retention** is an **ops** capability the schema-per-tenant model
  enables (per `multi-tenancy.arch.json`), executed against individual `t_<tenantId>` schemas
  — it is **not** a MIG responsibility and is out of scope here.
