# MIG — Integration Contracts

> MIG integrates with exactly **one** external system at runtime: **PostgreSQL**,
> over a single admin-capable datasource. It makes **no** outbound REST call, uses
> **no** broker, is **not** a Eureka client, and depends on **no** TechLab AI
> capability (doc 04 §External Integrations). Its only coupling to the business
> services is **offline / build-time**: it *applies* the `V00xx` scripts they
> *author*. This file pins (1) the PostgreSQL contract, (2) **how the authored
> scripts physically reach the runner (resolves doc 06 G2)**, (3) how provisioning is
> invoked, and (4) the **CI gate** that keeps every business service's Flyway
> disabled. EARS invariants `INV-MIG-1..7` are declared in `03-initial-domain-framing.md`.

## 1. PostgreSQL (the only runtime integration)

| Property | Value |
|---|---|
| Driver | `org.postgresql:postgresql` |
| Connection | one **admin-capable** datasource (`CREATE SCHEMA`, `CREATE EXTENSION`, DDL on all schemas) |
| Credential scope | lives **only** in the MIG job (secret-injected), never in a business service (doc 06 R9) |
| Pool | small; MIG is sequential and short-lived (A3) |

`THE SYSTEM SHALL connect to PostgreSQL through a single admin-capable datasource (A1).`
`THE SYSTEM SHALL confine the admin credential to the MIG job and SHALL NOT embed it in any business service (doc 06 R9).`
`THE SYSTEM SHALL build and run one Flyway instance per schema with the correct schemas/search_path/locations (ADR-002).`

## 2. Script-collection mechanism — resolves doc 06 G2 (recommendation, revisable)

**Problem (G2):** each data-owning service authors its DDL under
`backend/services/<svc>/src/main/resources/db/migration/`, but MIG is the sole runner
— so the authored scripts must physically reach MIG's classpath, reconciled into their
reserved blocks (ADR-003), without the local flat `V1__create_initial_schema.sql`
becoming a competing runtime artifact.

**Recommended mechanism — build-time aggregation into MIG classpath locations
(orchestrator default, revisable by the owner):**

- The runtime migration surface is a set of **MIG-owned classpath locations**, split
  by routing:
  - `classpath:db/migration/global` — all `-- schema: global` scripts (MIG baseline +
    each module's global block).
  - `classpath:db/migration/tenant` — all `-- schema: tenant` scripts (MIG tenant
    template + each module's tenant block).
- A **Gradle `copy`/aggregation task** in MIG's `build.gradle.kts` collects each
  module's reserved-block scripts (regenerated by `be-migration-generator.py` into
  that module's block, ADR-003) into the two MIG locations at build time, **renaming
  nothing** (the reserved block numbers are already globally unique, so there is no
  `V1` collision). The global pass points Flyway at `db/migration/global`; each tenant
  run points at `db/migration/tenant`.
- The flat local `V1__create_initial_schema.sql` is **not** on either MIG location and
  is **not** applied (it is deprecated generator scaffold — ADR-003).

> **Why build-time aggregation over reading each service's directory in place:** it
> gives one deterministic, inspectable migration surface in the MIG artifact (one jar
> carries exactly what will run), keeps the reserved-block numbering the single source
> of truth, and lets the CI gate (§4) assert that nothing flat-`V1` leaked in. Reading
> each `db/migration/` directory live would re-introduce the "which V1 wins?"
> ambiguity ADR-003 closes. **Alternative considered:** a composite Flyway
> `locations` list pointing at every service's directory — rejected because the flat
> `V1` files sit there and would be picked up. Revisable at Scaffold if the build
> topology changes.

`THE SYSTEM SHALL apply only the reserved-block, schema-annotated scripts aggregated into its own classpath locations, split global vs tenant (ADR-003).`
`THE SYSTEM SHALL NOT apply any flat V1__create_initial_schema.sql authored under a business service (ADR-003).`
`WHEN the global pass runs, THE SYSTEM SHALL use the db/migration/global location against neuroassist_global.`
`WHEN a tenant run runs, THE SYSTEM SHALL use the db/migration/tenant location against t_<tenantId> with neuroassist_global on search_path.`

## 3. How provisioning is invoked

Provisioning is **ops-triggered** (A5), never automatic at service startup and never
by a business service. A new care unit is onboarded by platform-ops running MIG:

```
java -jar neuroassist-niv-migrations.jar --provision-tenant <tenantId>
```

This creates `t_<tenantId>` outside any transaction (INV-MIG-6) and brings it to the
current version. A subsequent `--all` keeps it converged with the others. The schema
name is derived identically at the creation and application points as `t_<tenantId>`
(A4 / doc 06 R8); the tenant-id → schema-name derivation is owned jointly by MIG and
the provisioning path and documented once.

`WHEN platform-ops invokes --provision-tenant <tenantId>, THE SYSTEM SHALL create t_<tenantId> (if absent) outside any transaction and migrate it to the current version (INV-MIG-6).`
`THE SYSTEM SHALL derive the schema name as t_<tenantId> identically to the provisioning/creation point (A4, doc 06 R8).`
`THE SYSTEM SHALL NOT run automatically at any business service's startup (A5).`

## 4. CI gate — keep every business service's Flyway disabled

ADR-003 / doc 06 R2 require that MIG stays the **only** Flyway runner (INV-MIG-7). A
service could silently re-enable Flyway and apply its flat `V1`, diverging from the
central blocks. A CI gate (owned at Backlog/Scaffold as an operational issue) enforces
the invariant:

- Assert every `backend/services/*/src/main/resources/**/application*.yml` that is a
  Flyway-capable service sets `spring.flyway.enabled: false`.
- Assert no business service's build adds a Flyway *runner* at startup (MIG drives
  Flyway programmatically; others do not auto-run it).
- Assert no flat `V1__create_initial_schema.sql` leaked into MIG's aggregated
  locations (§2).

`THE SYSTEM SHALL be the only Flyway runner; every business service SHALL keep spring.flyway.enabled=false (INV-MIG-7, A2).`
`IF a business service enables Flyway or ships a startup Flyway runner, THEN THE CI gate SHALL fail the build.`
`IF a flat V1__create_initial_schema.sql appears in MIG's aggregated migration locations, THEN THE CI gate SHALL fail the build.`

## 5. Absent integrations (recorded, so scaffold wires none)

| Integration | Status |
|---|---|
| Eureka / service discovery | **absent** — MIG is not a client (ADR-002); REG lists MIG as "no dependency" |
| Message broker | **absent** — messaging disabled platform-wide |
| Outbound REST / Feign | **absent** — MIG calls no service |
| TechLab AI | **absent** — `ai.hasAi = false` |
| Blob / object storage | **absent** |

`THE SYSTEM SHALL integrate with PostgreSQL only and SHALL NOT open any discovery, broker, REST, AI, or storage integration.`
