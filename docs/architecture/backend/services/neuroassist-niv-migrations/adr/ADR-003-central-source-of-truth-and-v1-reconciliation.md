# ADR-003 — Central migration source of truth & local `V1` reconciliation

## Status
aceita

> Note: orchestrator default (recommendation) - revisable by the owner.

## Contexto

There are **two** candidate migration surfaces on disk and they must be reconciled:

1. **The reserved-block set.** Each data-owning service's doc 05 says it *authors* scripts in a
   reserved block (ACS `V0010–V0012`, PAT `V0020–V0022`, EDGE `V0030–V0032`, CONV
   `V0070–V0079`, …) that **MIG applies** across `neuroassist_global` + every `t_<tenantId>`,
   with no per-service runner.
2. **A local flat `V1`.** Every scaffolded service also ships
   `src/main/resources/db/migration/V1__create_initial_schema.sql`, generated by
   `be-migration-generator.py` from its `contracts/data-model.md` (carrying `-- schema:
   global|tenant` annotations). Verified present for acs, pat, edge, evnt, gest, hist, conv.

Left unreconciled this is dangerous: (a) every service has a **"V1"**, so naively pooling the
files into one Flyway location collides; (b) the flat `V1` numbering ignores the reserved
blocks; (c) the files sit where `spring.flyway.enabled: false`, so it is unclear who runs them
and when; (d) it is ambiguous how global vs tenant DDL is distinguished and how a *new* tenant
schema is brought up. The schema-per-tenant ADR is explicit that "the migrations service is the
single source of truth" — so a single answer is required.

## Decisão

- **MIG is the one runtime Flyway runner.** Business services keep `spring.flyway.enabled:
  false`; none migrates itself (INV-MIG-7). MIG applies the whole surface.
- **The reserved-block, schema-annotated scripts are the source of truth** — not the flat
  local `V1`. The per-service `V1__create_initial_schema.sql` is treated as **generator
  scaffold**: it is **regenerated into the module's reserved block** (ACS → `V0010–V0012`,
  PAT → `V0020–V0022`, …) and collected into MIG's central migration locations; the flat
  `V1` is then **deprecated and not applied**. (The exact collection mechanism — read each
  service's `db/migration/` directly vs. aggregate at build time — is doc 06 **G2**, settled
  at Specs/Scaffold.)
- **Global vs tenant is distinguished by the `-- schema:` annotation** (`persistence.arch.json`):
  the first line of each DDL block is `-- schema: global` or `-- schema: tenant`. Global blocks
  are applied to `neuroassist_global`; tenant blocks are applied to **every** `t_<tenantId>`
  from the same template set, so all tenants converge to one version.
- **Per-tenant schema templates are applied at provisioning.** `--provision-tenant <id>`
  creates `t_<id>` (outside a transaction — ADR-002) and runs the tenant-template blocks to
  the current version; a normal `--all` run also re-applies any newer tenant blocks to all
  existing `t_*`. Extensions live in `neuroassist_global`; tenant runs keep it on
  `search_path`.
- **Who runs Flyway at runtime:** **only MIG**, triggered by platform-ops (first start,
  deploy, provisioning) — never a business service, never automatically at service startup.

## Consequências

- **Positive:** one unambiguous runtime surface; no "which V1 wins?" collision; global/tenant
  routing is explicit and mechanical; new tenants are provisioned by the same path that
  migrates existing ones.
- **Positive:** the generator (`be-migration-generator.py`) stays useful (it authors the DDL
  from the data model) without its flat-`V1` output becoming a competing runtime artifact.
- **Negative / trade-off:** the scaffolded flat `V1` files must be migrated into reserved
  blocks and then kept inert (a CI guard that Flyway stays disabled in services, doc 06 R2);
  until that is done the two surfaces coexist and must not both be applied. Accepted as a
  one-time reconciliation owned by Backlog/Scaffold.
