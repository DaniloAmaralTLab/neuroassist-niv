# MIG — Structured Brief (source for Specs / Backlog / Scaffold)

> Module: **MIG — Migrations (Centralized Flyway, all schemas)** · Service: `neuroassist-niv-migrations` · Project: NeuroAssist NIV
> Stack: `java` (Java 21 / Spring Boot + Flyway + PostgreSQL, Gradle Kotlin DSL) · **Infrastructure**
> · No UI · No HTTP API · **Not a Eureka client** · Messaging: disabled.

1. **Canonical name / prefix:** `neuroassist-niv-migrations` (canonical `migrations`) /
   prefix `MIG`. **No server port** (runs as a one-shot job and exits).

2. **Problem it solves:** NeuroAssist NIV is **schema-per-tenant** PostgreSQL —
   `neuroassist_global` holds shared catalogues (users, RBAC, gesture vocabulary, pairing
   codes, audit-global) and every care unit lives in its own `t_<tenantId>` schema
   (`arch/decisions/multi-tenancy.arch.json`, `arch/decisions/persistence.arch.json`). Each
   business service **authors** its own DDL but **none of them runs Flyway** — every
   business `application.yml` ships `spring.flyway.enabled: false` with the comment
   *"Migrations gerenciadas pelo neuroassist-niv-migrations"* (verified on disk). MIG is the
   **single Flyway runner** that applies the whole migration surface — the global schema and
   **every** `t_<tenantId>` — in one deterministic, auditable pass. Without MIG no schema is
   created and the fleet cannot start.

3. **Personas:** no human end-user and no ACS role. Actors are the **platform/ops operator**
   (runs MIG before first fleet start, on each deploy, and at new-tenant provisioning;
   owns the datasource wiring) and the **business services** (indirect — they author scripts
   MIG applies and depend on the resulting schema being present and on-version).

4. **MVP scope (minimum viable):** one **Spring Boot runner job** (`MigrationsJobRunner`,
   `CommandLineRunner`) that (a) ensures required extensions and the `neuroassist_global`
   schema exist, (b) applies **global** migrations to `neuroassist_global`, (c) enumerates
   the existing `t_<tenantId>` schemas and applies the **tenant-template** migrations to each,
   (d) provisions a new `t_<tenantId>` schema and brings it to the current version when a
   tenant id is supplied, then **exits** with a non-zero code on any failure. Owns the
   **baseline block `V0001–V0009`** (extensions, `neuroassist_global`, `uuid_generate_v7()`,
   the `migration_range_registry` table, the per-tenant template baseline) and the
   authoritative **version-range registry** across all modules. Forward-only, checksum-validated.

5. **Out of MVP scope:** any business domain / entity / PHI; owning other modules' DDL
   (each service authors its own scripts — MIG only *applies* them); an HTTP/management API
   (MIG is a batch job, not a service); online/zero-downtime schema change orchestration;
   automated rollback/undo migrations (forward-only — see ADR-005); tenant **discovery**
   beyond "iterate `t_*` schemas / accept an explicit tenant id" (dynamic SaaS tenant
   onboarding workflow is owned by platform-ops / the tenant-provisioning path, not MIG);
   cross-tenant data migration/ETL.

6. **Mandatory external integrations:** **PostgreSQL** only — a single admin-capable
   datasource (`CREATE SCHEMA` / `CREATE EXTENSION` privileges) plus the per-run Flyway
   connections. **No outbound REST, no broker, no Eureka.** MIG is *not* a discovery client
   (REG records the Eureka clients as the business services + gateway; MIG is a job that runs
   and exits, so it never registers — `neuroassist-niv-service-registry/06` lists "no
   dependency on … MIG" and MIG reciprocally needs no registry).

7. **TechLab AI services depended on:** none (`ai.hasAi` not set for this module). Messaging
   disabled → MIG consumes and publishes **no** events; it coordinates with other modules
   purely through the shared database and the version-range registry, never at runtime.

8. **Anchor domain event:** **none** — MIG is infrastructure and owns no domain event. Its
   only lifecycle signal is operational: *"migrations applied"* (global + N tenant schemas
   brought to version V), surfaced as a job exit status / log line and as rows in
   `flyway_schema_history` per schema — not a NeuroAssist domain contract.

## Source material this module reconciles

- **Centralized-Flyway decision, already recorded by every data-owning service** — ACS, PAT,
  EDGE, EVNT, GEST, HIST, CONV, TRN each state in their `05-persistence-model.md` that they
  *author* scripts but MIG *applies* them across `neuroassist_global` + every `t_<tenantId>`,
  with **no per-service Flyway runner**.
- **Local `V1__create_initial_schema.sql` in each scaffolded service** — present under
  `backend/services/<svc>/src/main/resources/db/migration/` for acs, pat, edge, evnt, gest,
  hist, conv (generated by `be-migration-generator.py` from each `contracts/data-model.md`,
  with `-- schema: global|tenant` annotations). These use a **flat `V1`** that would collide
  across services if naively pooled, and Flyway is disabled where they sit. Reconciled in
  **ADR-003** (central source of truth) — they are generator scaffold, not the runtime
  migration surface.
- **Reserved version blocks already claimed by peers** (authoritative snapshot, EDGE spec
  §"Flyway reserved range" + each service's doc 05): ACS `V0010–V0012`, PAT `V0020–V0022`,
  EDGE `V0030–V0032` (rolling `V0033+`), CONV `V0070–V0079` (`V0077` seeds `conv.*`
  authorities), TRN **proposes** `V0080–V0089`. EVNT/GEST/HIST have **no numbered block yet**
  (open). MIG's `migration_range_registry` makes this list authoritative and closes **PAT
  gap G1**.
- **Multi-tenancy + persistence decisions** — `arch/decisions/multi-tenancy.arch.json`
  (schema-per-tenant, `globalSchema = neuroassist_global`, Hibernate `SCHEMA` strategy) and
  `arch/decisions/persistence.arch.json` (UUID v7 PKs, required extensions `uuid-ossp`,
  `pgcrypto`, `pg_trgm`, `unaccent`, the `-- schema:` DDL annotation that routes a block to
  its target schema). MIG's baseline block installs the extensions into `neuroassist_global`
  and every tenant run keeps the global schema on `search_path` (see ADR-003 / doc 05).

## Reserved block for MIG (decision, revisable)

| Block | Owner | Schema target | Content |
|---|---|---|---|
| `V0001–V0009` | **MIG** | `neuroassist_global` (+ per-tenant template baseline) | extensions, `neuroassist_global`, `uuid_generate_v7()`, `migration_range_registry`, tenant-template baseline / housekeeping |

> The orchestrator hint proposed `V0080–V0089` for MIG; that block is **already proposed by
> TRN** on disk, so reserving it would collide. MIG instead takes the **baseline block
> `V0001–V0009`** — the only block that *must* run before ACS's `V0010` (extensions + global
> schema are a precondition for every other module). This is the **orchestrator default
> (recommendation) — revisable by the owner** and is recorded in **ADR-004**.

- ADR-002 — Execution model: Spring Boot one-shot runner job, no HTTP port, not a Eureka client (**aceita**, recommendation — revisable).
- ADR-003 — Central migration source of truth & local `V1` reconciliation (**aceita**, recommendation — revisable).

## Notes for the following phases (Specs / Backlog / Scaffold)

- There is **no business API and no domain event contract** to spec. MIG's "contracts" are:
  (1) the **`migration_range_registry`** table shape + the current block assignments;
  (2) the **job CLI / run modes** (`--all`, `--global-only`, `--tenant <id>`,
  `--provision-tenant <id>`); (3) the **schema-routing convention** (`-- schema: global|tenant`).
- Scaffold owns `MigrationsJobRunner.java` (`CommandLineRunner`), `build.gradle.kts`
  (`flyway-core`, `postgresql`, **no** `spring-cloud-starter-netflix-eureka-client**`),
  `application.yml` (`spring.flyway.enabled: false` for the *auto* runner — MIG drives Flyway
  **programmatically** per schema; `spring.main.web-application-type: none`; no `server.port`;
  no `eureka.*`). Admin datasource with `CREATE SCHEMA`/`CREATE EXTENSION` rights.
- Backlog should produce **operational / infra** issues (baseline block, registry table,
  tenant-iteration loop, provisioning path, checksum/forward-only gate), **not** business-feature
  issues, and must reconcile the per-service local `V1` files (ADR-003) and confirm every
  reserved block against `migration_range_registry` (ADR-004) before emitting migration issues.
- **Known pitfalls to pre-empt** (Learning layer): never create/drop a schema inside the same
  `@Transactional` as a Flyway call (cross-connection deadlock); treat every committed `V*.sql`
  as applied and immutable (checksum) — fix forward, never edit in place; pick the next version
  as `max(global ∪ tenant histories) + 1`, never per-schema-local; prefix any MIG-owned table
  with `migration_` to avoid generic-name collisions in shared schemas.
