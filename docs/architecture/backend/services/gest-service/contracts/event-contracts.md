# GEST — Event Contracts

> Service: `gest-service` · Module **GEST** · Project: NeuroAssist NIV
> **Messaging disabled** (`stack.messaging.enabled = false`) — **no broker, no topics, no queues.**
> EARS authoring guide: `../../../standards/ears-notation.md`.

## 0. Transport

GEST publishes **no broker events** and **consumes none**. All cross-module contact is synchronous
REST (`hub-integration.md`). GEST's "domain events" are **audit records** written synchronously to
**HIST** with the shared audit envelope, inside the same request transaction boundary as the write
that produced them. There is no outbox and no eventual delivery.

EARS:

- THE SYSTEM SHALL NOT publish to, or consume from, any message broker (messaging is disabled project-wide).
- WHEN a GEST write succeeds (engine register/deprecate, capability declare/retire), THE SYSTEM SHALL record the corresponding audit fact to HIST within the same request (`hub-integration.md` §3).

## 1. Audit facts published to HIST (sync REST, shared envelope)

| Fact | Emitted by | Trigger |
|---|---|---|
| `EngineVersionRegistered` | `EngineVersionService` | `POST /gest/engines` succeeds |
| `EngineVersionDeprecated` | `EngineVersionService` | `POST /gest/engines/{version}/deprecate` succeeds (state actually changed) |
| `EngineCapabilityDeclared` *(anchor)* | `CapabilityService` | `POST /gest/capabilities` succeeds (create or status change) |
| `EngineCapabilityRetired` | `CapabilityService` | `POST /gest/capabilities/{id}/retire` succeeds (state actually changed) |

### 1.1 Envelope (shared HIST audit envelope)

```json
{
  "eventType": "EngineCapabilityDeclared",
  "occurredAt": "2026-11-20T12:00:00Z",
  "correlationId": "<X-Correlation-Id>",
  "actorId": "<jwt.sub>",
  "actorType": "caregiver",
  "source": "gest-service",
  "subjectType": "engine_capability",
  "subjectId": "<capability-uuid>",
  "payload": {
    "engineVersion": "1.3.0",
    "gestureTypeCode": "BLINK",
    "supportStatus": "supported",
    "previousSupportStatus": "experimental"
  }
}
```

`EngineVersionRegistered` / `EngineVersionDeprecated` carry `subjectType = "engine_version"`,
`subjectId = <engine-version-uuid>`, and a payload of `{ "version", "displayLabel", "status" }`.

## 2. Idempotency of audit writes

- **Key:** `(source, subjectType, subjectId, eventType, occurredAt)` — HIST upserts on it, so a
  retried audit after a client timeout does not duplicate.
- **Window:** bounded by the request; GEST does not retry audit across requests (no outbox). On
  HIST failure for a write, **all four GEST facts are hard-502** under HIST ADR-005
  (`../../hist-service/adr/ADR-005-audit-write-failure-policy.md`; see `hub-integration.md` §3):
  roll back + `502 audit-unavailable` (fail-closed). GEST has no access-ending or safety facts, so no
  commit+durable-retry case applies.

## 3. Payload versioning

- `payload` objects are **additive-only**; new optional fields may be added without a version bump.
- A breaking change bumps `eventType` with a suffix (`EngineCapabilityDeclared.v2`) — not expected
  for this thin, stable registry.

EARS:

- WHEN GEST records an audit fact, THE SYSTEM SHALL set `source = "gest-service"` and `correlationId` to the request's `X-Correlation-Id` (generated by GWY if absent).
- THE SYSTEM SHALL include `previousSupportStatus` on `EngineCapabilityDeclared` whenever the declare changed an existing row, so HIST can reconstruct the support timeline.
