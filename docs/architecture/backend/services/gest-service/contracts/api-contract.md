# GEST — API Contract

> Service: `gest-service` · Module **GEST — Gesture Detection (Edge)** · Project: NeuroAssist NIV
> Stack: Java 21 / Spring Boot (hexagonal — `../../../adr/ADR-001-hexagonal-architecture.md`,
> key `hexagonal_java`) · **Global schema** `neuroassist_global` (INV-GEST-3) · Messaging disabled.
> EARS authoring guide: `../../../standards/ears-notation.md`.

GEST is an **ACS resource server**: it validates JWKS-trusted JWTs and never issues tokens. It
owns the two global aggregates `EngineVersion` and `EngineCapability` and exposes an **advisory,
read-mostly** surface under base path **`/gest`**. The registry is **global** (INV-GEST-3): the same
rows are disclosed to every caller and **no endpoint derives a per-tenant answer**; the JWT
`tenantId` claim is never used to scope GEST data.

---

## 0. Conventions

- **Base path:** `/gest`. GWY (API Gateway) fronts the service; paths below are as seen by the controller.
- **Media type:** `application/json`. Errors use `application/problem+json` (RFC 7807, §4).
- **Identifiers:** all resource ids are UUID (string, canonical form). `version` is a free-form
  engine release string (e.g. `1.3.0`), **unique**, and is the external key of `EngineVersion`.
- **Authority model (D-639):** fine-grained authorities are `gest.<resource>.<action>`, English
  canonical. Reads use the action `.read` (never `.view`); mutations use `.create` / `.retire`
  (never `.register` / `.edit`). Sourced from the single `RoleAuthorityPolicy` (SPEC-06); controller
  `@PreAuthorize` strings MUST equal those constants (D-535).
- **One application service per path root (D-640):** `/gest/engines` → `EngineVersionService`,
  `/gest/capabilities` → `CapabilityService`. No third path root is introduced.
- **Declared resource (D-641):** the permission `resource` differs from the service name `gest`, so
  it is declared explicitly: `engine` for `/gest/engines`, `capability` for `/gest/capabilities`.
- **State-changing verbs:** `POST` only (declare / deprecate / retire are modelled as commands on a
  resource). `GET` is side-effect free. The registry is append + soft-retire (never `DELETE`).

### 0.1 Mandatory headers

| Header | Direction | Rule |
|---|---|---|
| `Authorization: Bearer <jwt>` | request | Required on **every** `/gest` endpoint. GEST has no public endpoint and issues no token. |
| `X-Correlation-Id` | request/response | Propagated end-to-end; generated by GWY if absent, echoed on the response and on every HIST audit call. |
| `X-Tenant-Id` | — | **Never trusted, and never used.** GEST is global (INV-GEST-3); it does not scope data by tenant. |
| `If-None-Match` | request | Optional on reads (§3) and on `support-check`; enables conditional `304` for station/consumer caching (ADR-004 pattern). |
| `ETag` | response | Returned on reads and on `support-check` for edge/consumer caching, keyed by engine version. |

EARS — headers & auth:

- WHEN a `/gest` endpoint receives a request without a valid `Authorization` bearer token, THE SYSTEM SHALL respond `401 Unauthorized`.
- IF a request supplies an `X-Tenant-Id` header, THEN THE SYSTEM SHALL ignore it and SHALL NOT scope any response by tenant (INV-GEST-3).
- THE SYSTEM SHALL echo the received `X-Correlation-Id` on every response and on every downstream HIST audit call.
- WHEN a mutating request bears a token whose `jti` is revoked (verified via ACS introspection on write paths), THE SYSTEM SHALL respond `401 Unauthorized`.

### 0.2 JWT claims consumed (JWKS-trusted; issued in the ACS trust domain)

| Claim | Used by GEST for |
|---|---|
| `sub` | actor id → `declared_by` on writes; audit `actorId` |
| `actorType` | `caregiver` \| `patient-session` \| `device` \| `service-client` — read vs write gate selection |
| `authorities` | `gest.*` authority checks (SPEC-06) |
| `jti` | revocation check via ACS `/acs/auth/introspect` on **write** paths only (reads are not revocation-sensitive — advisory global data) |

> `tenantId` is intentionally **not** consulted. GEST stores and returns the same global rows to all tenants.

## 1. Authorities and caller identities

### 1.1 Authority catalog (the complete set GEST declares)

| Authority | Action | Resource (D-641) | Endpoints | Who holds it |
|---|---|---|---|---|
| `gest.engine.read` | read | `engine` | `GET /gest/engines`, `GET /gest/engines/{version}` | admin caregiver, PAT/DASH service-client, **station (`edge.device`)** |
| `gest.engine.create` | create | `engine` | `POST /gest/engines` | admin caregiver only |
| `gest.engine.retire` | retire | `engine` | `POST /gest/engines/{version}/deprecate` | admin caregiver only |
| `gest.capability.read` | read | `capability` | `GET /gest/capabilities`, `GET /gest/capabilities/{id}`, `POST /gest/capabilities/support-check` | admin caregiver, patient-session, PAT/DASH service-client, **station (`edge.device`)** |
| `gest.capability.create` | create | `capability` | `POST /gest/capabilities` | admin caregiver only |
| `gest.capability.retire` | retire | `capability` | `POST /gest/capabilities/{id}/retire` | admin caregiver only |

> No operation is named `read` (D-639: `read` is the **action**, never the operation name). The
> bulk station read is the operation `checkSupport` carrying authority `gest.capability.read`.

EARS — write gate (INV-GEST-5):

- IF a request to any `POST /gest/engines*` or `POST /gest/capabilities*` **write** path bears a token that lacks the required `gest.*.create`/`gest.*.retire` authority (e.g. a patient-session or `edge.device` read-only token), THEN THE SYSTEM SHALL respond `403 Forbidden` and SHALL NOT mutate the registry.

### 1.2 Station authentication decision (`edge.device` token vs caregiver JWT)

**Decision: the patient station authenticates all GEST reads — including the primary
`support-check` (§3.3) — with its `edge.device` token**, not a caregiver / patient-session JWT. The
`edge.device` token MUST carry the read authorities `gest.capability.read` and `gest.engine.read`.

Justification:

1. **Timing / availability.** The "detectable" gate (§3.3) must be computable at station
   **bootstrap / catalog-load**, independent of — and typically **before** — any active patient
   session. The `edge.device` token is the only identity the station always holds (it already uses
   it for the EDGE heartbeat and `GET /edge/catalog`). Requiring a patient-session JWT would couple
   a product-reference read to session lifecycle and break the boot-time gate.
2. **Data sensitivity / least privilege.** The registry is **global, non-PII, advisory**
   (INV-GEST-3/4): it discloses the same truth to every caller and holds no patient data. A machine
   (device) identity is sufficient; no patient-scoped authority is warranted.
3. **Single station identity.** Reusing the `edge.device` token keeps every station *machine* read
   under one identity (EDGE catalog **and** GEST support-check), avoiding a second token acquisition
   on the detection-critical path.

A patient-session ACS JWT (which also carries `gest.*`, per ACS INV-3 / PAT INV-7) is **accepted as
a fallback** during an active session; GEST validates both via the same JWKS. The requirement that
the `edge.device` token carry `gest.capability.read` / `gest.engine.read` is an **INT item handed to
ACS/EDGE** — see `integration-contracts.md` §6 (**INT-GEST-ACS-1**). GEST owns no part of token
minting.

EARS:

- WHEN the station presents a JWKS-trusted `edge.device` token bearing `gest.capability.read` to `support-check`, THE SYSTEM SHALL resolve support exactly as for a caregiver read (the answer is global; identity does not change it).
- WHERE a read request presents any JWKS-trusted token bearing the required `gest.*.read` authority, THE SYSTEM SHALL serve the read regardless of `actorType` (INV-GEST-3; the registry is not tenant- or actor-scoped).

## 2. Engine versions — `/gest/engines` (service `EngineVersionService`, resource `engine`)

### 2.1 `GET /gest/engines` — list engine versions (authority `gest.engine.read`)

Query: `?status=active|deprecated|all` (default `active`). Response `200 OK` (+ `ETag`):

```json
{ "engines": [
  { "version": "1.3.0", "displayLabel": "NeuroAssist Detector 1.3", "status": "active",
    "createdAt": "2026-11-20T12:00:00Z" } ] }
```

EARS:

- WHEN a caller with `gest.engine.read` lists engine versions, THE SYSTEM SHALL return the global set filtered by `status`, identical for every tenant (INV-GEST-3).
- THE SYSTEM SHALL return an `ETag` derived from the result set so consumers may issue conditional `GET` with `If-None-Match`.

### 2.2 `GET /gest/engines/{version}` — get one engine version (authority `gest.engine.read`)

Response `200 OK`: a single engine object (as §2.1). `404 engine-version-not-found` if absent.

### 2.3 `POST /gest/engines` — register an engine version (authority `gest.engine.create`)

Request:

```json
{ "version": "1.3.0", "displayLabel": "NeuroAssist Detector 1.3" }
```

Response `201 Created` (+ `Location: /gest/engines/1.3.0`):

```json
{ "version": "1.3.0", "displayLabel": "NeuroAssist Detector 1.3", "status": "active",
  "createdAt": "2026-11-20T12:00:00Z" }
```

EARS:

- WHEN an admin caller with `gest.engine.create` registers a new `version`, THE SYSTEM SHALL create it with `status = active`, record `EngineVersionRegistered` to HIST within the same request, and respond `201 Created`.
- IF the `version` already exists, THEN THE SYSTEM SHALL respond `409 engine-version-conflict` and SHALL NOT create a duplicate (`version` is unique).

### 2.4 `POST /gest/engines/{version}/deprecate` — deprecate an engine version (authority `gest.engine.retire`)

Response `200 OK`: the engine object with `status = deprecated`.

EARS:

- WHEN an admin caller with `gest.engine.retire` deprecates an `active` engine version, THE SYSTEM SHALL set `status = deprecated`, record `EngineVersionDeprecated` to HIST, and respond `200 OK`.
- WHILE an engine version is `deprecated`, THE SYSTEM SHALL keep its existing capability rows resolvable for reads and `support-check` (stations still on it must keep self-checking), and SHALL reject new capability declarations against it with `409 engine-version-deprecated` (§3.4).
- IF the engine version is already `deprecated`, THEN THE SYSTEM SHALL respond `200 OK` idempotently (no state change, no duplicate audit).

## 3. Capabilities — `/gest/capabilities` (service `CapabilityService`, resource `capability`)

### 3.1 `GET /gest/capabilities` — list / filter capabilities (authority `gest.capability.read`)

Query (all optional, AND-combined): `?engineVersion=1.3.0&code=BLINK&supportStatus=supported`.
Passing only `engineVersion` returns the **full support map for that engine version** — the
secondary, cacheable "bulk by engine version" read. Response `200 OK` (+ `ETag`):

```json
{ "engineVersion": "1.3.0",
  "capabilities": [
    { "id": "<uuid>", "engineVersion": "1.3.0", "gestureTypeCode": "BLINK",
      "supportStatus": "supported", "notes": null,
      "declaredBy": "<caregiverId>", "declaredAt": "2026-11-20T12:00:00Z",
      "updatedAt": "2026-11-20T12:00:00Z" } ] }
```

EARS:

- WHEN a caller with `gest.capability.read` lists capabilities, THE SYSTEM SHALL return the matching global rows and an `ETag` derived from the result set (INV-GEST-3).
- WHEN `If-None-Match` matches the current `ETag`, THE SYSTEM SHALL respond `304 Not Modified` with no body.

### 3.2 `GET /gest/capabilities/{id}` — get one capability (authority `gest.capability.read`)

Response `200 OK`: a single capability object (as §3.1). `404 capability-not-found` if absent.

### 3.3 `POST /gest/capabilities/support-check` — **PRIMARY station read** (authority `gest.capability.read`)

The station sends its running `engineVersion` plus the set of `GestureType` codes it needs to gate
(typically every primitive referenced by the loaded EDGE catalog). GEST answers per code. This is the
**"detectable" gate** the station uses to mark a command "not yet detectable".

Request:

```json
{ "engineVersion": "1.3.0", "codes": ["BLINK", "DOUBLE_BLINK", "BROW_RAISE"] }
```

Response `200 OK` (+ `ETag` keyed by `engineVersion` and the resolved result):

```json
{ "engineVersion": "1.3.0",
  "results": [
    { "code": "BLINK",        "supportStatus": "supported",    "detectable": true },
    { "code": "DOUBLE_BLINK", "supportStatus": "experimental", "detectable": true },
    { "code": "BROW_RAISE",   "supportStatus": "unknown",      "detectable": false } ] }
```

**INV-GEST-7 (the "detectable" gate — declared here, contract-layer, cited elsewhere as INV-GEST-7).**

EARS:

- WHEN the station calls `support-check` with an `engineVersion` and a list of `codes`, THE SYSTEM SHALL return, for **each requested code**, its `supportStatus` for that engine version, treating the **absence of a row as `unknown`** (never an error, never omitted).
- THE SYSTEM SHALL derive `detectable = (supportStatus ∈ {supported, experimental})`, so that `unsupported` and `unknown` both yield `detectable = false`.
- WHERE `engineVersion` is unknown to the registry, THE SYSTEM SHALL still respond `200 OK` with every requested code resolved to `unknown` / `detectable = false` (a station on an unrecognised engine detects nothing certified — advisory, not an error).
- THE SYSTEM SHALL return an `ETag` so the station can cache the result keyed by `engineVersion` and re-validate with `If-None-Match` (`304` when unchanged); the registry is read-mostly, so cache hits are the common case.
- IF `codes` is empty or absent, THEN THE SYSTEM SHALL respond `400 validation-error`.
- THE SYSTEM SHALL compute compound-command detectability **nowhere**: it returns per-code truth only; a compound command is `detectable` on the station iff **all** its primitive codes are `detectable` (station-side AND; see `integration-contracts.md` §4).

> Why `POST` for a read: the request carries a variable-length code set (a body), and the answer is
> cached application-side via `ETag`, not by HTTP intermediaries. §3.1 (`GET ?engineVersion=`) remains
> available as the fully HTTP-cacheable full-dump alternative.

### 3.4 `POST /gest/capabilities` — declare / re-declare a capability (authority `gest.capability.create`)

Upserts the single row for `(engineVersion, gestureTypeCode)`. Request:

```json
{ "engineVersion": "1.3.0", "gestureTypeCode": "BLINK",
  "supportStatus": "supported", "notes": "stable since 1.2" }
```

Response `201 Created` (new row) or `200 OK` (status change to the same pair); body as §3.1.

EARS:

- WHEN an admin caller with `gest.capability.create` declares support for `(engineVersion, gestureTypeCode)` with `supportStatus ∈ {supported, experimental}`, THE SYSTEM SHALL validate that `gestureTypeCode` exists in PAT's global vocabulary via `GET /pat/gesture-types` (INV-GEST-1) before persisting.
- IF `gestureTypeCode` is not present in PAT's vocabulary, THEN THE SYSTEM SHALL respond `400 gesture-type-code-unknown` and SHALL NOT persist.
- IF PAT's vocabulary endpoint is unavailable at declare time, THEN THE SYSTEM SHALL **fail closed** with `503 pat-vocabulary-unavailable` (+ `Retry-After`) and SHALL NOT persist (a declaration is rare and admin-driven; an unvalidated code must never enter the registry).
- WHEN the pair does not yet exist, THE SYSTEM SHALL insert it, record `EngineCapabilityDeclared` to HIST, and respond `201 Created`; WHEN it exists, THE SYSTEM SHALL update `supportStatus`/`notes` + `updatedAt`, record `EngineCapabilityDeclared`, and respond `200 OK` (INV-GEST-2: one row per pair).
- IF the target engine version is `deprecated`, THEN THE SYSTEM SHALL respond `409 engine-version-deprecated` and SHALL NOT declare new support.
- WHERE the existing row is terminal (`supportStatus = unsupported`) and the request moves it back to `supported`/`experimental`, THE SYSTEM SHALL treat this as an **explicit, audited re-declare** (allowed; INV-GEST-6 forbids only *silent* re-support) and record `EngineCapabilityDeclared`.

### 3.5 `POST /gest/capabilities/{id}/retire` — retire a capability (authority `gest.capability.retire`)

Response `200 OK`: the capability with `supportStatus = unsupported`.

EARS:

- WHEN an admin caller with `gest.capability.retire` retires a capability, THE SYSTEM SHALL set `supportStatus = unsupported` (terminal), retain the row for audit/history, record `EngineCapabilityRetired` to HIST, and respond `200 OK` (INV-GEST-6).
- IF the capability is already `unsupported`, THEN THE SYSTEM SHALL respond `200 OK` idempotently (no duplicate audit).
- THE SYSTEM SHALL never physically delete a capability or engine-version row (append + soft-retire).

## 4. Errors (RFC 7807 `application/problem+json`)

All error bodies are `ProblemDetail` with `type`, `title`, `status`, `detail`, `instance`, and the
echoed `correlationId`.

| HTTP | `type` slug | When |
|---|---|---|
| 400 | `validation-error` | malformed body; empty `codes` on support-check |
| 400 | `gesture-type-code-unknown` | declare with a code absent from PAT vocabulary (INV-GEST-1) |
| 401 | `unauthorized` | missing/invalid token; revoked `jti` on a write path |
| 403 | `forbidden` | read-only token on a write path (INV-GEST-5) |
| 404 | `engine-version-not-found` | unknown `version` on `GET /gest/engines/{version}` |
| 404 | `capability-not-found` | unknown `id` on capability get/retire |
| 409 | `engine-version-conflict` | duplicate `version` on create |
| 409 | `engine-version-deprecated` | declare against a deprecated engine version |
| 503 | `pat-vocabulary-unavailable` | PAT vocabulary unreachable at declare time (fail closed) |

EARS:

- WHEN any endpoint rejects a request, THE SYSTEM SHALL return `application/problem+json` with a stable `type` slug (table above) and the echoed `X-Correlation-Id` as `correlationId`.

---

## 5. Enums (valid Java identifiers — no leading digits)

- `SupportStatus` = `supported` | `experimental` | `unsupported`. `unknown` is **not** stored — it is
  the *absence* of a row, surfaced only by `support-check` (§3.3).
- `EngineStatus` = `active` | `deprecated`.

> `engineVersion` values (e.g. `1.3.0`) are free-form strings, never enum constants, so leading-digit
> release ids are fine as data; no enum constant begins with a digit.
