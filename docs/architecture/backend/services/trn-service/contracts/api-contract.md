# TRN — API Contract

> Service: `trn-service` · Module **TRN — AI-Assisted Training (Speech Tree Authoring)** · Project: NeuroAssist NIV
> Stack: Java 21 / Spring Boot (hexagonal — `../../../adr/ADR-001-hexagonal-architecture.md`,
> key `hexagonal_java`) · Multi-tenant (schema-per-tenant) · Messaging **disabled** · English-only.
> EARS authoring guide: `../../../standards/ears-notation.md`.

TRN is an **ACS resource server** on all of its endpoints — it validates the ACS-minted **caregiver**
JWT via ACS JWKS and mints no token of its own. It holds a **service-client** token to call CONV / PAT
/ HIST (never a patient or user token). Tenant context on every authenticated endpoint derives from the
JWT `tenantId` claim (INV-TRN-8); `X-Tenant-Id` is never trusted. **Nothing on this surface is on the
patient's live communication path** — a TRN or vendor outage never affects CONV runtime (INV-TRN-9).

The **patient/guardian assent** half of the dual authorization is **not** a `trn.*` authority and the
patient-session token (restricted to `conv.*`/`gest.*`, ACS INV-3) is **never** accepted here — assent
is recorded in-session as a domain fact (ADR-002; see §4.2). Keeping ACS INV-3 intact is a deliberate
revisable decision (R1): a future owner choice to give the patient a scoped `trn.*` on the
patient-session token is recorded as an open future option, **not** implemented in v1.

---

## 0. Conventions

- **Base path:** `/trn`. GWY (API Gateway) fronts the service; paths below are as seen by the controller.
- **Media type:** `application/json`; errors use `application/problem+json` (RFC 7807).
- **Identifiers:** all resource ids are UUID (canonical string form); `assetId` is a stable manifest id.
- **Authority model:** fine-grained authorities follow `trn.<resource>.<action>`, sourced from the
  single `RoleAuthorityPolicy` (SPEC-06). Controller `@PreAuthorize` strings MUST equal those constants
  (D-535, D-639). `@EnableMethodSecurity(prePostEnabled = true)` is mandatory (D-642).
- **State-changing verbs** map to `POST` / `DELETE` only; `GET` is side-effect free. Lifecycle
  transitions are modelled as sub-resource `POST`s (e.g. `/caregiver-confirmation`), not in-place edits.
- **No public endpoints** other than `GET /trn/health` (SPEC-07). Every other endpoint requires the ACS
  caregiver token.

### 0.1 Mandatory headers

| Header | Direction | Rule |
|---|---|---|
| `Authorization: Bearer <jwt>` | request | Required on every endpoint except `GET /trn/health` (public). Must be the ACS **caregiver** token; a patient-session token is rejected `403` (ACS INV-3). |
| `X-Correlation-Id` | request/response | Propagated end-to-end; generated by GWY if absent, echoed on the response and on every downstream CONV/PAT/HIST call. |
| `X-Tenant-Id` | — | **Never trusted from the request.** Tenant context is derived from the JWT `tenantId` claim only (INV-TRN-8). |
| `Idempotency-Key` | request | Optional on `POST .../publication`; defaults to `trn:publish:<approvalId>` (§5, INV-TRN-6). |

EARS — headers & auth:

- WHEN a protected TRN endpoint receives a request without a valid `Authorization` bearer token, THE SYSTEM SHALL respond `401 Unauthorized`.
- IF a request supplies an `X-Tenant-Id` header, THEN THE SYSTEM SHALL ignore it and derive tenant context exclusively from the JWT `tenantId` claim (INV-TRN-8).
- IF a request presents a patient-session token (authorities restricted to `conv.*`/`gest.*`), THEN THE SYSTEM SHALL respond `403 Forbidden` on every `/trn` endpoint (ACS INV-3, ADR-002).
- THE SYSTEM SHALL echo the received `X-Correlation-Id` on every response and on every downstream CONV/PAT/HIST call.

### 0.2 Token types

| Token | Issuer | `actorType` | Used on | Validated via |
|---|---|---|---|---|
| caregiver | ACS | `caregiver` / `clinic_coordinator` | all `/trn` endpoints (§1–§7) | ACS JWKS (TRN is a resource server) |
| service-client (TRN→) | ACS | `service-client` | outbound to CONV/PAT/HIST (held by TRN, not accepted inbound) | — (see `integration-contracts.md`) |

## 2. Sessions

### 2.1 `POST /trn/sessions` — open a training session (authority `trn.session.create`)

Opens an authoring session bound to one patient. TRN first resolves the patient via PAT
(`pat.patient.read`, ETag/304) to confirm existence/tenant before creating the session.

Request:

```json
{ "patientId": "<uuid>" }
```

Response `201 Created` (+ `Location: /trn/sessions/{sessionId}`):

```json
{ "sessionId": "<uuid>", "patientId": "<uuid>", "status": "open",
  "openedBy": "<caregiver-uuid>", "openedAt": "2026-11-22T10:00:00Z" }
```

EARS:

- WHEN a caregiver with `trn.session.create` opens a session for a patient in their tenant, THE SYSTEM SHALL resolve the patient via PAT, create one `open` `training_session`, respond `201 Created`, and audit `TrainingSessionStarted` to HIST (hard-502 — ADR-007).
- IF the `patientId` does not resolve in the caller's tenant via PAT, THEN THE SYSTEM SHALL respond `404 Not Found` type `patient-not-found` and create no session (no cross-tenant disclosure — INV-TRN-8).
- IF the HIST audit of `TrainingSessionStarted` fails, THEN THE SYSTEM SHALL roll back the session creation and respond `502 Bad Gateway` type `audit-unavailable` (hard-502 — ADR-007).

### 2.2 `GET /trn/sessions/{sessionId}` — read a session (authority `trn.session.read`)

Response `200 OK` with the session and its proposals' ids/states.

EARS:

- WHEN a caregiver reads a session in their tenant, THE SYSTEM SHALL return the session with the id and `state` of each proposal.
- IF `{sessionId}` does not exist in the caller's tenant, THEN THE SYSTEM SHALL respond `404 Not Found` (INV-TRN-8).

## 3. Assistant dialog and proposals

### 3.1 `POST /trn/sessions/{sessionId}/dialog` — an assistant dialog turn (authority `trn.proposal.update`)

Submits the caregiver's intent for a turn; TRN calls `LlmDialogPort` (Anthropic) with **minimised**
context only — draft category/phrase text and the caregiver prompt; **never** a patient name, PHI or
free-text identifier (`patientId` only, INV-TRN-7). The model output is **untrusted draft data**: it may
only create/refine proposals in `draft`/`proposed` (INV-TRN-2); it can never set an authority, select a
tenant, flip an approval, or trigger a publish/erase.

Request:

```json
{ "prompt": "<caregiver authoring intent>", "turnRef": "<opaque client turn id>" }
```

Response `200 OK`:

```json
{ "sessionId": "<uuid>",
  "proposals": [
    { "proposalId": "<uuid>", "type": "phrase", "text": "I need suction", "parentRef": "cat-care", "state": "proposed" }
  ],
  "assistantMessage": "<model summary, stored as data, never executed>" }
```

EARS:

- WHEN a caregiver submits a dialog turn, THE SYSTEM SHALL call `LlmDialogPort` with minimised context (draft text + prompt, `patientId` only, no name/PHI/free-text identifier) and SHALL create or refine proposals only in `draft`/`proposed` state (INV-TRN-2, INV-TRN-7, ADR-004).
- THE SYSTEM SHALL treat the model response as data and SHALL NOT let it set an authority, select a tenant, change a proposal `state` beyond `proposed`, or trigger a publish/erase (prompt-injection containment — ADR-004, INV-TRN-2).
- IF the Anthropic provider is unavailable, THEN THE SYSTEM SHALL respond `503 Service Unavailable` type `llm-unavailable`, create no proposal, and leave the session resumable (ADR-007); no approval, publish or CONV runtime is affected.
- THE SYSTEM SHALL NOT retain the raw model transcript as a compliance record — only the minimal draft content persists (ADR-004/ADR-007).

### 3.2 `GET /trn/sessions/{sessionId}/proposals/{proposalId}` — read a proposal (authority `trn.proposal.read`)

Response `200 OK` with the proposal and its `authorization` value object (which halves are present).

### 3.3 `PATCH /trn/sessions/{sessionId}/proposals/{proposalId}` — refine a draft proposal (authority `trn.proposal.update`)

Human edit of a `draft`/`proposed` proposal's `label`/`text`/`parentRef`.

EARS:

- WHEN a caregiver edits a proposal in `draft` or `proposed`, THE SYSTEM SHALL update its draft content and keep it in `draft`/`proposed` (INV-TRN-2).
- IF the proposal is in `approved` or any state at/after the gate, THEN THE SYSTEM SHALL respond `409 Conflict` type `proposal-state-locked` (a change after approval is a new proposal — ADR-003).

## 4. Dual authorization (the human-only gate — ADR-002/ADR-003)

A proposal reaches `approved` only when **both** the caregiver confirmation (§4.1) and the
patient/guardian assent (§4.2) are present **and recorded by distinct actors** (INV-TRN-1). Neither half
alone crosses the gate. `ProposalApproved` is the anchor event (audited hard-502).

### 4.1 `POST /trn/proposals/{proposalId}/caregiver-confirmation` — caregiver half (authority `trn.proposal.approve`)

The authenticated caregiver confirms the proposal. `confirmedBy` is taken from the token subject (never
from the body).

Response `200 OK` with the proposal (state `caregiver_approved` or `approved` if the patient half is
already present).

EARS:

- WHEN a caregiver with `trn.proposal.approve` confirms a `proposed`/`patient_approved` proposal, THE SYSTEM SHALL record `caregiver_confirmed_by` = token subject and `caregiver_confirmed_at`, and transition the proposal to `caregiver_approved` (or `approved` if the patient assent is already recorded by a distinct actor).
- IF recording the caregiver half would make `caregiver_confirmed_by` equal to an existing `patient_confirmed_by`, THEN THE SYSTEM SHALL respond `409 Conflict` type `dual-authorization-same-actor` and record nothing (INV-TRN-1).

### 4.2 `POST /trn/proposals/{proposalId}/patient-assent` — patient/guardian assent fact (authority `trn.proposal.approve`)

Records the patient half as a **domain fact** (ADR-002) — captured in-session by the supervising
caregiver, attributed to the patient or a **legal guardian**. `confirmedBy` MUST differ from the
caregiver who confirmed §4.1.

Request:

```json
{ "confirmedBy": "<patient-or-guardian-ref>",
  "method": "gesture",
  "evidenceRef": "blob://trn/.../assent-evidence",
  "relationship": "legal-guardian" }
```

`relationship` is omitted when the patient self-assents; set (with evidence) when a guardian substitutes
for a non-verbal patient.

Response `200 OK` with the proposal (state `patient_approved` or `approved`).

EARS:

- WHEN a patient/guardian assent is recorded for a `proposed`/`caregiver_approved` proposal with a `confirmedBy` distinct from the caregiver half, THE SYSTEM SHALL store `{confirmedBy, method, evidenceRef, relationship?, patient_confirmed_at}` and transition the proposal to `patient_approved` (or `approved` if the caregiver half is already present).
- WHEN both halves are present and recorded by distinct actors, THE SYSTEM SHALL transition the proposal to `approved` and audit `ProposalApproved` to HIST (hard-502 — the governance pivot, ADR-007).
- IF `confirmedBy` equals the caregiver who supplied §4.1, THEN THE SYSTEM SHALL respond `409 Conflict` type `dual-authorization-same-actor` (INV-TRN-1).
- THE SYSTEM SHALL NOT accept a patient assent via a `trn.*` authority on a patient-session token — the assent is a domain fact only (ADR-002, ACS INV-3).

### 4.3 `POST /trn/proposals/{proposalId}/rejection` — reject a proposal (authority `trn.proposal.reject`)

Transitions `proposed`/`caregiver_approved`/`patient_approved` → `rejected` (terminal).

EARS:

- WHEN a caregiver with `trn.proposal.reject` rejects a non-terminal, pre-`approved` proposal, THE SYSTEM SHALL set its state `rejected` and respond `200 OK`.
- IF the proposal is already `approved` or terminal, THEN THE SYSTEM SHALL respond `409 Conflict` type `proposal-state-locked`.

### 4.4 `POST /trn/proposals/{proposalId}/withdrawal` — withdraw a proposal (authority `trn.proposal.update`)

Transitions `draft`/`proposed`/`approved` → `withdrawn` (terminal). Withdrawing an `approved` proposal
before publication is allowed (a change is a new proposal, ADR-003).

EARS:

- WHEN a caregiver withdraws a `draft`/`proposed`/`approved` (not yet `published`) proposal, THE SYSTEM SHALL set its state `withdrawn` and respond `200 OK`.
- IF the proposal is `published`, THEN THE SYSTEM SHALL respond `409 Conflict` — a published version is immutable; use erasure (§7).

## 5. Voice-cloning consent (ADR-005)

### 5.1 `POST /trn/consents` — capture voice-cloning consent (authority `trn.consent.create`)

Captures consent of the **patient and legal representative**, before any synthesis (INV-TRN-3).

Request:

```json
{ "patientId": "<uuid>", "scope": "voice_cloning",
  "grantedByPatient": true, "grantedByRepresentative": true,
  "representativeRef": "<rep-ref>", "evidenceRef": "blob://trn/.../consent-evidence" }
```

Response `201 Created` (+ `Location: /trn/consents/{consentId}`).

EARS:

- WHEN a caregiver captures a `voice_cloning` consent with both `grantedByPatient` and `grantedByRepresentative` true, THE SYSTEM SHALL create a `granted` `consent_record`, respond `201 Created`, and audit `ConsentGranted` to HIST (hard-502 — must be durable before synthesis, ADR-007).
- IF either half of the consent is missing (patient or representative), THEN THE SYSTEM SHALL respond `422 Unprocessable Entity` type `incomplete-consent` and create no `granted` record (INV-TRN-3).

### 5.2 `GET /trn/patients/{patientId}/consent` — read the patient's consent (authority `trn.consent.read`)

Response `200 OK` with the current `consent_record` (or `404` if none).

### 5.3 `POST /trn/consents/{consentId}/revocation` — revoke consent (authority `trn.consent.revoke`)

Revocation is **never blocked** (commit + durable-retry, ADR-007, INV-TRN-9) and stops future synthesis.

Response `200 OK` (`{ "consentId": "<uuid>", "status": "revoked", "revokedAt": "..." }`).

EARS:

- WHEN a caregiver revokes a `granted` consent, THE SYSTEM SHALL set its status `revoked`, respond `200 OK`, and audit `ConsentRevoked` to HIST via durable-retry — committing the revocation even if HIST is unreachable (commit + durable-retry, never blocked — ADR-007, INV-TRN-9).
- WHILE a consent is `revoked`, THE SYSTEM SHALL refuse any new `TtsPort` synthesis for the patient (INV-TRN-3).
- IF the consent is already `revoked`, THEN THE SYSTEM SHALL respond `200 OK` with no state change (idempotent).

## 6. Synthesize, index and publish (ADR-005/ADR-006/ADR-003)

### 6.1 `POST /trn/proposals/{proposalId}/publication` — synthesize + index + publish an approved proposal (authority `trn.publication.create`)

Triggers the broker-free pipeline for an `approved` proposal: synthesize the phrase via `TtsPort`
(consent-gated), index approved content via `SearchIndexPort`, and publish the immutable version to CONV
(`POST /conv/trees`, service-client `conv.tree.publish`, idempotency `trn:publish:<approvalId>`). The
work runs as durable-retry jobs (ADR-007); the endpoint returns immediately.

Response `202 Accepted` (+ `Location: /trn/publications/{publicationId}`):

```json
{ "publicationId": "<uuid>", "approvalId": "<uuid>", "patientId": "<uuid>",
  "idempotencyKey": "trn:publish:<approvalId>", "status": "pending" }
```

EARS:

- WHEN a caregiver requests publication of an `approved` proposal, THE SYSTEM SHALL create at most one `publication` per approval (idempotent on `trn:publish:<approvalId>`), enqueue the synthesize→index→publish jobs, and respond `202 Accepted` (INV-TRN-6).
- IF the proposal is not `approved`, THEN THE SYSTEM SHALL respond `409 Conflict` type `not-approved` and start nothing (ADR-003, INV-TRN-2).
- IF no `granted`, non-revoked voice-cloning consent exists for the patient, THEN THE SYSTEM SHALL respond `409 Conflict` type `consent-required` and not call `TtsPort` (INV-TRN-3, ADR-005).
- THE SYSTEM SHALL NOT publish a version to CONV while any approved phrase lacks an `available` synthesized `audio_asset` in the same version (no dangling ref; CONV would reject `422` — INV-TRN-4).
- WHEN the publication request repeats an `approvalId` already published, THE SYSTEM SHALL respond `202 Accepted`/`200 OK` with the existing `publication` and create no duplicate (INV-TRN-6, aligns CONV SPEC-05).
- WHEN CONV is unreachable at publish time, THE SYSTEM SHALL retain the `approved` proposal and retry the publish idempotently (`trn:publish:<approvalId>`) until CONV accepts — never blocking and never affecting CONV runtime (ADR-007, INV-TRN-9).
- WHEN Elasticsearch is unavailable, THE SYSTEM SHALL retry indexing but SHALL still proceed with the publish to CONV (indexing never blocks publishing — ADR-006).

### 6.2 `GET /trn/publications/{publicationId}` — read publication status (authority `trn.publication.read`)

Response `200 OK` with `{ publicationId, approvalId, status (pending|published|failed), convVersionId?, lastError?, publishedAt? }`.

EARS:

- WHEN a publish job has completed, THE SYSTEM SHALL return `status = published` with the `convVersionId` returned by CONV and audit `ContentPublished` to HIST (hard-502 — ADR-007).

## 7. Erasure — right-to-be-forgotten (ADR-005/ADR-006)

### 7.1 `DELETE /trn/patients/{patientId}/content` — erase a patient's authored voice content (authority `trn.content.delete`)

Deletes the ElevenLabs voice model, **crypto-shreds** the per-subject key (voice samples, audio refs,
`voice_model_ref` become unreadable), marks TRN rows `erased`, retires affected CONV versions
(`conv.tree-version.retire`) and requests CONV audio erasure (`DELETE /conv/patients/{patientId}/audio`,
`conv.audio.delete`). Erasure is **never blocked** by a HIST/CONV outage.

Response `202 Accepted`:

```json
{ "patientId": "<uuid>", "status": "ERASING",
  "erasedSampleCount": 12, "erasedAssetCount": 40, "retiredVersionCount": 3 }
```

EARS:

- WHEN a caregiver with `trn.content.delete` requests erasure for a patient, THE SYSTEM SHALL delete the ElevenLabs voice model, delete the per-subject key (crypto-shred), mark `voice_model`/`voice_sample`/`audio_asset` `erased`, enqueue `conv.tree-version.retire` + `conv.audio.delete`, respond `202 Accepted`, and audit `VoiceModelDeleted`/`ContentErased` to HIST (commit + durable-retry — ADR-005/ADR-006).
- WHEN HIST or CONV is unreachable at erasure time, THE SYSTEM SHALL complete the local crypto-shred, enqueue the retire/erase/audit facts on `outbound_job`, respond `202 Accepted`, and retry idempotently until accepted — erasure is never blocked (ADR-007, INV-TRN-9).
- WHEN content for the patient has already been erased, THE SYSTEM SHALL respond `202 Accepted` with zero counts (idempotent).
- THE SYSTEM SHALL retain the immutable governance records with their payload rendered unreadable (not hard-deleted — HIST ADR-006).

## 9. Error model (RFC 7807)

All errors are `application/problem+json`. Project-wide model: `../../../standards/` /
`arch/decisions/error-model.arch.json`. TRN-specific `type` slugs:

| `type` | Status | When |
|---|---|---|
| `patient-not-found` | 404 | `patientId` not resolvable in tenant (§2.1) |
| `proposal-state-locked` | 409 | edit/transition illegal for the current state (§3.3, §4) |
| `dual-authorization-same-actor` | 409 | both halves by the same actor (§4, INV-TRN-1) |
| `incomplete-consent` | 422 | consent missing patient or representative half (§5.1, INV-TRN-3) |
| `consent-required` | 409 | synthesis requested without granted consent (§6.1, INV-TRN-3) |
| `not-approved` | 409 | publication requested for a non-`approved` proposal (§6.1) |
| `dangling-audio-reference` | 422 | internal guard before publish; a phrase lacks its asset (INV-TRN-4) |
| `llm-unavailable` | 503 | Anthropic provider down (§3.1, ADR-007) |
| `audit-unavailable` | 502 | a hard-502 HIST audit failed (§2.1, §4.2, §6.2 — ADR-007) |

EARS:

- THE SYSTEM SHALL return every error as `application/problem+json` with a stable `type`, `title`, `status`, and a correlation-friendly `instance`, and SHALL NOT leak vendor error bodies or other tenants' data.
