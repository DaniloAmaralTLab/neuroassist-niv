# ACS — API Contract

> Service: `acs-service` · Module **ACS — Caregivers and Access** · Project: NeuroAssist NIV
> Stack: Java 21 / Spring Boot (hexagonal — `../../../adr/ADR-001-hexagonal-architecture.md`,
> key `hexagonal_java`) · Multi-tenant (schema-per-tenant) · Messaging disabled.
> EARS authoring guide: `../../../standards/ears-notation.md`.

ACS is the platform's **authorization server**: it authenticates caregivers, issues
tenant-scoped JWTs, manages caregiver↔patient links, governs the patient-with-session
lifecycle, and owns the stateless-JWT revocation blacklist. Every other resource server
trusts ACS-issued tokens.

---

## 0. Conventions

- **Base path:** `/acs`. GWY (API Gateway) fronts the service; paths below are as seen
  by the controller.
- **Media type:** `application/json`. Errors use `application/problem+json` (RFC 7807).
- **Identifiers:** all resource ids are UUID (string, canonical form).
- **Authority model:** fine-grained authorities follow `acs.<resource>.<action>`, sourced
  from the single `RoleAuthorityPolicy` (SPEC-06). Controller `@PreAuthorize` strings MUST
  equal those constants (INV-7).
- **State-changing verbs** map to `POST`/`DELETE` only (domain-framing convention).

### 0.1 Mandatory headers

| Header | Direction | Rule |
|---|---|---|
| `Authorization: Bearer <jwt>` | request | Required on every endpoint except `POST /acs/auth/login` and `GET /acs/.well-known/jwks.json`. |
| `X-Correlation-Id` | request/response | Propagated end-to-end; generated by GWY if absent and echoed on the response and on the HIST audit call. |
| `X-Tenant-Id` | — | **Never trusted from the request.** Tenant context is derived from the JWT `tenantId` claim only. |

EARS — headers & auth:

- WHEN a protected endpoint receives a request without a valid `Authorization` bearer token, THE SYSTEM SHALL respond `401 Unauthorized`.
- WHEN a request carries a bearer token whose `jti` is on the blacklist, THE SYSTEM SHALL respond `401 Unauthorized`.
- IF a request supplies an `X-Tenant-Id` header, THEN THE SYSTEM SHALL ignore it and derive tenant context exclusively from the JWT `tenantId` claim.
- THE SYSTEM SHALL echo the received `X-Correlation-Id` on every response and on every downstream HIST audit call.

### 0.2 JWT claims (issued tokens)

| Claim | Meaning |
|---|---|
| `sub` | subject id — caregiver id (caregiver token) or patient-session id (session token) |
| `tenantId` | tenant (care-unit) id — present on caregiver and patient-session tokens; absent for `platform-ops` |
| `actorType` | `caregiver` \| `patient-session` \| `platform-ops` |
| `authorities` | array of authority strings from `RoleAuthorityPolicy` |
| `jti` | token identifier — the key used by the revocation blacklist |

EARS — issuance:

- WHEN ACS issues a caregiver token, THE SYSTEM SHALL set `tenantId` to the caregiver's tenant and `authorities` to the caregiver role's authority set (SPEC-06).
- WHEN ACS issues a patient-session token, THE SYSTEM SHALL restrict `authorities` to `conv.*` / `gest.*` only and SHALL NOT include any `acs.*` authority (INV-3).

## 1. Authentication

### 1.1 `POST /acs/auth/login` — authenticate (public)

Resolves login → tenant deterministically (INV-6), verifies the credential, issues a
caregiver JWT, and audits `CaregiverAuthenticated`.

Request:

```json
{ "username": "ana.silva", "password": "••••••••" }
```

Response `200 OK`:

```json
{ "accessToken": "<jwt>", "tokenType": "Bearer", "actorType": "caregiver", "tenantId": "<uuid>", "caregiverId": "<uuid>" }
```

EARS:

- WHEN valid credentials are presented, THE SYSTEM SHALL resolve the login to exactly one tenant, issue a caregiver JWT, and respond `200 OK`.
- IF the credential is invalid or the caregiver is `deactivated`, THEN THE SYSTEM SHALL respond `401 Unauthorized` with ProblemDetail type `invalid-credentials` (no distinction between the two cases, to avoid user enumeration).
- WHEN authentication succeeds, THE SYSTEM SHALL audit a `CaregiverAuthenticated` action to HIST before returning the token.

### 1.2 `GET /acs/.well-known/jwks.json` — public key set (public)

Returns the JSON Web Key Set resource servers use to verify ACS-issued signatures.

- THE SYSTEM SHALL expose the active signing public key(s) as a JWKS document.

### 1.3 `POST /acs/auth/introspect` — blacklist-aware validation (service client)

For service-to-service validation that must also honor revocation. Authority: service
client only (`platform-ops` or an internal resource-server client).

Request: `{ "token": "<jwt>" }` → Response `200 OK`: `{ "active": true, "sub": "...", "actorType": "...", "tenantId": "...", "authorities": [ ... ] }`.

- WHEN the presented token is well-formed, unexpired and its `jti` is not blacklisted, THE SYSTEM SHALL respond `active: true`.
- IF the token's `jti` is blacklisted, THEN THE SYSTEM SHALL respond `active: false`.

## 2. Caregivers

### 2.1 `POST /acs/caregivers` — register (authority `acs.caregiver.create`)

Request:

```json
{ "username": "carlos.lima", "password": "••••••••", "role": "caregiver" }
```

Response `201 Created` (+ `Location: /acs/caregivers/{id}`):

```json
{ "id": "<uuid>", "tenantId": "<uuid>", "username": "carlos.lima", "role": "caregiver", "status": "active" }
```

EARS:

- WHEN a caller with `acs.caregiver.create` registers a caregiver, THE SYSTEM SHALL create it in the caller's tenant with `status = active` and respond `201 Created`.
- THE SYSTEM SHALL set the new caregiver's `tenantId` to the authenticated caller's tenant and SHALL ignore any tenant supplied in the body (INV-1).
- IF the `username` already exists globally, THEN THE SYSTEM SHALL respond `409 Conflict` with ProblemDetail type `username-taken` (INV-6).
- IF `role` is not one of `caregiver` / `clinic_coordinator`, THEN THE SYSTEM SHALL respond `400 Bad Request`.

### 2.2 `DELETE /acs/caregivers/{id}` — deactivate (authority `acs.caregiver.deactivate`)

Soft deactivation (record retained; login blocked).

Response `204 No Content`.

EARS:

- WHEN a caller with `acs.caregiver.deactivate` deactivates a caregiver of their tenant, THE SYSTEM SHALL set `status = deactivated`, retain the row, and respond `204 No Content`.
- IF the target caregiver belongs to a different tenant, THEN THE SYSTEM SHALL respond `404 Not Found` (tenant isolation — no cross-tenant existence disclosure).
- WHILE a caregiver is `deactivated`, THE SYSTEM SHALL reject that caregiver's `POST /acs/auth/login` attempts with `401 Unauthorized`.

### 2.3 `GET /acs/caregivers/me` — current caregiver profile (authenticated caregiver)

Response `200 OK`: `{ "id", "tenantId", "username", "role", "status" }`.

## 3. Caregiver ↔ Patient links

### 3.1 `POST /acs/caregivers/{caregiverId}/links` — link patient (authority `acs.patient-link.link`)

Request: `{ "patientId": "<uuid>" }` → Response `201 Created`: `{ "id", "caregiverId", "patientId" }`.

EARS:

- WHEN a caller with `acs.patient-link.link` links a patient to a caregiver of the same tenant, THE SYSTEM SHALL create the authorization edge and respond `201 Created`.
- IF the `(caregiverId, patientId)` link already exists, THEN THE SYSTEM SHALL respond `409 Conflict` (idempotent re-link — SPEC-05).
- IF the `caregiverId` is not in the caller's tenant, THEN THE SYSTEM SHALL respond `404 Not Found`.

### 3.2 `DELETE /acs/caregivers/{caregiverId}/links/{patientId}` — unlink (authority `acs.patient-link.unlink`)

Response `204 No Content`.

- WHEN a caller with `acs.patient-link.unlink` removes an existing link, THE SYSTEM SHALL delete the edge and respond `204 No Content`.
- IF the link does not exist, THEN THE SYSTEM SHALL respond `404 Not Found`.

### 3.3 `GET /acs/caregivers/{caregiverId}/links` — list links (authenticated caregiver)

Response `200 OK`: `{ "links": [ { "patientId": "<uuid>" } ] }`.

## 4. Patient sessions

### 4.1 `POST /acs/patient-sessions` — provision (authority `acs.patient-session.provision`)

Provisions a **non-expiring**, revocable patient session (ADR-012 Option C). Anchor
action **PatientSessionProvisioned**.

Request:

```json
{ "patientId": "<uuid>", "deviceId": "<uuid>" }
```

Response `201 Created`:

```json
{ "id": "<uuid>", "tenantId": "<uuid>", "patientId": "<uuid>", "deviceId": "<uuid>",
  "status": "active", "sessionToken": "<jwt>", "provisionedBy": "<caregiverId>" }
```

EARS:

- WHEN a caller with `acs.patient-session.provision` provisions a session for a patient of their tenant, THE SYSTEM SHALL create an `active` session, mint a patient-session JWT restricted to `conv.*` / `gest.*`, and respond `201 Created` (INV-2, INV-3).
- THE SYSTEM SHALL record `provisionedBy` as the authenticated caregiver's id.
- THE SYSTEM SHALL issue a session JWT without an expiry claim (non-expiring by design — ADR-003).
- IF the `patientId` or `deviceId` is not valid within the caller's tenant, THEN THE SYSTEM SHALL respond `404 Not Found`.
- WHEN provisioning succeeds, THE SYSTEM SHALL audit `PatientSessionProvisioned` to HIST within the same request.

### 4.2 `DELETE /acs/patient-sessions/{id}` — revoke (authority `acs.patient-session.revoke`)

Terminal, immediate revocation (ADR-003, SEC-001). Counterpart **PatientSessionRevoked**.

Response `204 No Content`.

EARS:

- WHEN a caller with `acs.patient-session.revoke` revokes an `active` session, THE SYSTEM SHALL set `status = revoked`, add the session token `jti` to the blacklist in the same transaction, and respond `204 No Content` (INV-4).
- WHEN a session is revoked, THE SYSTEM SHALL cause the next request bearing that session token to be rejected with `401 Unauthorized` (immediate invalidation).
- IF the target session is already `revoked`, THEN THE SYSTEM SHALL respond `204 No Content` (idempotent revoke — SPEC-05).
- THE SYSTEM SHALL NOT reactivate a `revoked` session; re-enabling access requires a new provision (INV-4).
- WHEN revocation succeeds, THE SYSTEM SHALL audit `PatientSessionRevoked` to HIST within the same request.

### 4.3 `GET /acs/patient-sessions/{id}` — read session status (authenticated caregiver)

Response `200 OK`: `{ "id", "patientId", "deviceId", "status", "provisionedBy", "revokedBy", "createdAt", "revokedAt" }`.

## 5. Tenant onboarding (platform-ops)

### 5.1 `POST /acs/ops/tenants` — onboard (authority `acs.tenant.onboard`)

Sole tenant-creation path (ADR-011; INV-5). Caller is the tenantless `platform-ops`
service client.

Request: `{ "type": "family", "name": "Família Silva" }` → Response `201 Created`:
`{ "id": "<uuid>", "type": "family", "name": "Família Silva" }`.

EARS:

- WHEN `platform-ops` onboards a tenant, THE SYSTEM SHALL create the global `tenant` row and trigger provisioning of the `t_<tenantId>` schema via MIG, and respond `201 Created`.
- IF any actor other than `platform-ops` (i.e. any token lacking `acs.tenant.onboard`) calls this endpoint, THEN THE SYSTEM SHALL respond `403 Forbidden` (INV-5).
- IF `type` is not one of `family` / `clinic`, THEN THE SYSTEM SHALL respond `400 Bad Request`.

## 6. Error model (RFC 7807)

All errors return `application/problem+json`:

```json
{ "type": "https://neuroassist/errors/<slug>", "title": "<short>", "status": 409,
  "detail": "<human message>", "instance": "/acs/caregivers", "correlationId": "<id>" }
```

| `type` slug | HTTP | Raised by |
|---|---|---|
| `invalid-credentials` | 401 | `POST /acs/auth/login` |
| `unauthenticated` | 401 | any protected endpoint, missing/invalid/blacklisted token |
| `forbidden` | 403 | authority check failed |
| `not-found` | 404 | cross-tenant or missing resource |
| `username-taken` | 409 | `POST /acs/caregivers` |
| `link-exists` | 409 | `POST .../links` |
| `validation-error` | 400 | malformed body / bad enum |

EARS — error surface:

- THE SYSTEM SHALL return `application/problem+json` with a stable `type` URI, the HTTP `status`, and the request `correlationId` for every error response.
- IF an authority check fails, THEN THE SYSTEM SHALL respond `403 Forbidden` and SHALL NOT reveal whether the target resource exists.
